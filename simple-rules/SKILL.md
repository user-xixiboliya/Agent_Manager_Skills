# Simple Rules：每条规则都有用途，先讲清再修改

## 触发与范围

- 只有用户在输入中显式调用 `/simple-rules` 时，才启用本规范。
- 用户没有调用时，不因任务涉及控制、公式、求解器或规则而自动启用；引用或讨论这个 skill 的名称也不算调用。
- 适合通过人工编写的模型、目标函数、约束和条件分支实现行为的算法：控制、规划、调度、拟合、数值优化等，领域不限。
- 例如模型预测控制（MPC）根据状态和模型预测未来，求解一段满足约束的动作；内点法是处理约束优化问题的一类数值求解方法。两者只是例子，不预设项目采用了哪一种算法。
- 普通深度学习训练不是主要适用场景；混合系统中需要审查人工规则时，只对那部分应用本规范。
- 只要求解释或分析时保持只读。调用本 skill 不代表同意新增、删除、合并规则、修改参数或启动实际部署。
- 用户在本轮的明确要求优先；已有明确授权的内容不重复询问，遇到授权外的行为变化再确认。

## 核心原则

### 精简且有效，不按数量决定好坏

目标是让每条规则职责明确、作用可验证，整个行为容易理解和调试。规则少但失效、把多个条件压进难懂的一行、把复杂逻辑藏进函数或配置，都不算有效精简。

允许新增确实有用的规则，但必须说明它解决什么已查证的问题或明确需求、为什么现有机制覆盖不了或需要这个机制、如何验证效果，由用户认为合理并明确同意后才能添加。没有实测时，说明依据是推导或待验证假设，不能承诺收益。

### 分清不同性质的规则

| 类型 | 在算法中的作用 | 审查重点 |
|---|---|---|
| 模型和目标函数 | 描述系统或拟合关系，以及要优化什么 | 假设是否适用、量纲和尺度是否一致、目标是否体现真实需求 |
| 可行性与安全约束 | 限制结果必须满足的物理、业务或安全条件 | 来源、适用范围、与其他约束是否冲突、是否真的被执行 |
| 数值求解条件 | 支持求解器有效运行，如有效定义域、终止条件 | 对应算法的必要条件和实现依据，不能笼统当作多余分支 |
| 人工启发式与补丁 | 为特定情况直接改变候选、输出或执行行为 | 是否重复、互相抵消、掩盖根因，是否引入更多例外 |

先调查每条规则属于哪类。数学必要条件、物理限制和安全约束不能仅为减少数量而删掉；来源或必要性查不清的，说明不确定性并与用户商议。

### 先解释因果，再考虑补规则

追踪“输入 → 建模或候选生成 → 求解或选择 → 后处理 → 执行 / 输出 → 反馈”的实际路径，检查行为从哪一步开始偏离预期。路径随项目调整，不强行添加组件。

对异常先检查相关模型假设、输入、接口、单位、目标、约束和求解状态。比较修正原有机制、复用已有约束与新增规则的可行性；不只因某个现象看起来异常，就增加阈值、惩罚项、裁剪或豁免分支。

复杂规则并非一律禁止；确有必要时，说明复杂性从哪里来、哪些部分不可省，以及使用和维护的代价。不能用“这样更稳健”代替依据。

## 沟通规范

- 先解释整体任务和组件角色，再解释具体规则。公式先说明算什么、在流程哪一步、输出给谁用，然后解释符号、单位、适用假设和边界。
- 规则用行为描述命名，例如“限制相邻两次输出的变化”；代码变量或函数名只在说明作用后附上，便于核对。
- 与用户商议时，先说功能是什么、做什么用、基于什么假设、为何当前需要决定，再说明选项的效果、代价、与项目原有约定的关系及是否需要额外授权。选项标题和提问工具描述也遵守此要求。
- 报告和后续追问继续用直白的行为描述；不能因前面解释过一次，就改用一串变量名、缩写或自造简称。用户没懂时重新解释或举例。
- “这几项多余”必须逐项解释：每项原本做什么、依据什么条件判断多余、改掉后会怎样、还有什么未确认。数量和结论均须来自实际调查。
- 事实、推断和建议分别表达；自己先前说错或用户理解与证据矛盾时，主动指出并纠正。

## 执行流程

### 先只读理清逻辑

1. 阅读项目约定、相关入口、配置、调用方和现有验证材料。外部实现或资源缺失时向用户确认，不猜版本、接口、路径或默认行为。
2. 说明整体任务、实际输入输出、组件关系及反馈依赖；区分上层想完成的任务和底层一次求解或调用实际能完成什么。
3. 只列本次行为涉及的规则，沿实际执行顺序看它们如何共同作用。规则在多处出现时，检查是否同一来源、是否重复生效、谁最后决定输出。
4. 用推导、代码路径、已有日志或授权的复现实验判断问题来源；静态检查不能直接证明运行改善。没有复现条件时说明证据边界。

从零设计新算法时，先说明目标行为、输入输出、成立假设和必要约束；已有规则和旧行为不存在的项明确写“不适用”。新增规则对应可验证的需求，不强行虚构旧实现或故障。

相关规则可用下面的简表整理；不要求额外新建规则清单文件：

| 规则（直白描述） | 作用位置与输入输出 | 目的、假设及来源 | 生效条件与行为影响 | 与其他规则的关系 | 已知证据 / 待确认 |
|---|---|---|---|---|---|

### 提出最小有效改动，等用户确认

对拟新增、删除、合并或修改的规则，先完整解释：

```text
当前行为：现在做什么，哪里与需求不符
问题依据：代码、原文、推导或复现结果；仍不确定的地方
建议改动：用直白语言描述，每项放在哪一步、影响哪些输入和输出
必要性：解决什么问题，现有机制为何不足，有没有更简单的方案
作用范围：什么时候生效，什么时候不该生效；与已有规则怎样配合
代价与风险：计算负担、响应或精度影响、冲突和安全边界
验证办法：用哪些对照或场景判断有用，怎样识别误触发或副作用
需要确认：具体改动范围，阈值或权重的含义及建议，验收标准
```

给出基于调查的推荐，不替用户决定。数值和验收阈值不写死，解释含义、单位和依据后与用户商定。用户理解并明确同意前，不先写代码、改配置或参数，也不先加分支再事后说明。

用户只说“解释一下”“继续分析”时，继续只读；确认必须对应具体改动。默认不要求额外做复杂表单或堆积决策文档，回复或项目已有记录能讲清即可。

### 按已确认范围修改并验证

- 改动集中在职责对应的位置，优先复用同一套规则来源，避免上下游重复判断或多套阈值各自生效。相关配置、调用方和已有测试一起核对。
- 用可区分原因的最小改动验证假设。多个改动确实必须一起做时，事先说明依赖和共同验证的方法，不机械要求逐个拆开。
- 按已确认规则选择场景：应生效、不应生效、边界，以及确有关系的规则相互作用。修改已有算法时，与原行为在可比条件下对照；从零设计时，按已确认的需求、必要约束和验收条件验证。
- 关注任务实际需要的行为质量、约束满足和计算代价；仅能运行或完成任务不能代替规则有效性证据。具体指标由任务和用户确认决定。
- 优先使用项目已有测试和日志；缺少观测时，先商议最小必要信息，如导致改变输出的条件、改变前后值和求解状态。避免逐字段检查或大量日志本身增加调试负担。
- 没有测试条件时如实报告未验证，不能宣布行为已改善。验证失败先分析原因，需要新规则或超范围修改时，重新解释并等用户确认。
- 不为调试自行增加行为开关；确有需要时说明用途并征得用户同意，默认行为由用户设定。
- 实际部署或真机试验另外确认范围和安全条件；本 skill 的代码修改确认不包含实际执行授权。

## 报告方式

用直白语言讲清“原行为与问题依据 → 已确认的改动及必要性 → 实际验证效果、代价和未覆盖范围”。按复杂度适度使用表格，避免每项只剩代码名称。

| 改动（行为描述） | 为什么需要 | 验证结果与代价 | 证据及未覆盖范围 |
|---|---|---|---|

仅完成分析时，明确哪些是待确认建议；完成修改时，区分用户确认过的内容与仍未实施的建议。不在每次报告中重复整套规则清单，不擅自建立额外记录文件。

## 调用示例

```text
/simple-rules 先分析这段求解与后处理逻辑，解释每条规则的用途，提出精简方案；与我确认后再改。
```

## 完成前检查

- [ ] 整体流程、关键组件、接口和相关规则的共同作用已讲清
- [ ] 模型、必要约束、求解条件和人工补丁已区分，未凭数量判定多余
- [ ] 每项改动都有明确问题、假设、作用范围、代价和验证办法
- [ ] 新增、删除、合并、参数和超范围改动均在实施前得到具体确认
- [ ] 未靠叠加特例掩盖根因，也未为精简擅自去掉必要或安全条件
- [ ] 结果有推导或实测依据，未验证与未覆盖范围明确
- [ ] 报告没有未经解释的变量名和缩写，前后矛盾已纠正
- [ ] 没有未经同意的开关、额外规则记录或实际部署行为
