## 触发与范围

### 触发规则

- 只有用户在输入中显式调用 `/train-preflight` 时，才启用本规范。
- 用户没有调用时，不主动套用本规范，即使任务看起来是在准备训练。
- 一旦调用，本规范在本轮任务内全程有效，直到最终报告完成。

### 适用场景

- 新的训练任务第一次上卡，不知道 batch size 能开多大、要占多少硬盘
- 换了模型、数据、序列长度、分辨率或卡，原来的配置不一定还合适
- 训练要跑很久，需要能在中断后接着训练
- 之前的训练 OOM 过，或者显存只用了一小半

### 不适用场景

- 只做推理或评估，不训练
- 用户已经给定全部参数，只要求直接启动训练

用户在本轮的明确要求与本规范冲突时，以用户要求为准，并在最终报告中写明。

## 和 env-first 的关系

本规范需要知道机器的情况：GPU 型号和显存、能用哪几张卡、卡是否和别人共用、工作空间在哪里、磁盘剩余多少。

1. 先读项目根目录 AGENTS.md 或 CLAUDE.md 里的“运行环境”一节。
2. 缺少上面这些信息时，按 env-first 的方法补查。
3. 没有安装 env-first 时，至少运行 `hostname`、`nvidia-smi`、`df -h <工作空间>`，并在回复中写出命令和关键输出。

关于机器的结论都要有命令输出作为依据。没查过的写“未检查”，命令失败的写“无法确认”。

## 显存目标

- **以什么为准**：以 `nvidia-smi` 中本进程的显存峰值为准。这个数字包含 CUDA 自身的固定开销，以及 PyTorch 预留但暂时没用的缓存，最接近“这张卡还剩多少”。同时用 `torch.cuda.max_memory_reserved()` 交叉核对。
- **目标值**：显存目标 = 这张卡实际可用的显存 − 余量。“实际可用”是总显存减去别的进程已经占用的部分。
- **必须留余量**：不能把配置调到“刚好不 OOM”。冒烟测试只跑了有限的步数，正式训练中还可能遇到更长的样本、评估阶段、越来越多的碎片、别人占用的变化，余量就是留给这些没测到的波动的。
- **余量不用留太多，也没有固定值**：冒烟测试覆盖得越全，需要的余量越小。具体留多少，由 agent 结合下面的情况给出建议值和理由，在确认点 2 和用户商定；冒烟测试后发现实际情况和预想不同（例如碎片比预想的明显），在确认点 4 重新商量。
- **可以少留的情况**：
  - 冒烟测试覆盖了最坏情况，包括最长的样本（或最大分辨率）、评估阶段、保存 checkpoint 的那一步
  - 卡由本任务独占
  - 输入大小固定，预留显存和实际使用的显存接近
- **需要多留的情况**：
  - 最坏情况没法在冒烟测试中覆盖，例如样本长度没有上限
  - 卡和别人共用，别人的占用会变化
  - 显存碎片明显：预留显存比实际使用的显存高出很多
- 商定的余量和理由写进最终报告。

## 核心原则

### 原则一：结论要有实测依据

估算只用来排除明显不可行的配置，例如权重和优化器状态就已经放不下。最终采用的 batch size、显存峰值、吞吐、硬盘占用，都以冒烟测试的实测结果为准，并在报告中写明测量方法和结果文件的位置。

### 原则二：参数分两类，会改变训练结果的必须先问

| 类别 | 例子 | 处理方式 |
|---|---|---|
| 只影响速度和显存 | 保持等效 batch 不变，调整每卡 batch 和梯度累积步数；开关梯度检查点；DataLoader 的 worker 数、`pin_memory`、`prefetch_factor`；评估时的 batch size；显存分配器参数 | agent 可以自己调，全部写进报告 |
| 会改变训练结果 | 等效 batch；学习率、warmup、学习率调度；数值精度（fp32、fp16、bf16）；序列截断长度、图像分辨率；优化器种类；数据采样方式 | 必须先问用户，给出选项和推荐理由 |

等效 batch = 每卡 batch × 梯度累积步数 × 卡数。判断不清属于哪一类时，按第二类处理。ZeRO、FSDP、offload 这类一般不改变结果、但改动大的方案，也要先问用户。

### 原则三：不写静默兜底

- 正式训练中不能捕获 OOM 后自动缩小 batch 继续跑。冒烟测试中为了找上限可以捕获 OOM，但只在测试脚本里，不进正式训练代码。
- 续训时用户指定的 checkpoint 不存在或读不出来，直接报错，不能悄悄从头开始。
- 只有设成“自动找最新 checkpoint”，并且输出目录里确实一个都没有时，才可以从头训练，而且要打印明确的日志，写明找过哪个目录。
- 恢复时关键配置和 checkpoint 不一致，直接报错，不自动改配置去迁就。
- GPU 不可用时不退回 CPU，找不到权重时不改用随机初始化。

agent 认为确实需要兜底时，先问用户；用户同意后才写，触发时必须输出明确的日志。

### 原则四：产物分开存放，不删除，不覆盖

- 冒烟测试的产物和正式训练分开存放，具体位置见 smoke-test.md。
- 不覆盖已有的运行目录；目标目录已存在时先问用户。
- agent 不删除、不移动、不重命名任何实验产物，包括冒烟测试自己生成的；在最终报告中列出，交给用户处理。
- 临时脚本和诊断输出放在 `.agents/tmp/`，任务结束时列给用户。
- 缓存不写进产物目录。

### 原则五：只改准备工作需要的代码

修改训练代码只限于三类：显存和吞吐测量、断点续训、把需要调整的参数暴露到配置或命令行。和这三类无关的代码，即使看起来可以优化，也不改，写进最终报告的“建议”。

## 确认点

整个流程中有四个确认点。到达确认点时，必须停下来等用户回复，不能自行继续。

| 确认点 | 时机 | 需要确认的内容 |
|---|---|---|
| 确认点 1 | 开始前（阶段 A 结束） | 训练入口和配置文件、用哪几张卡、正式训练的总步数或 epoch 数、产物目录、哪些参数允许调整、当前等效 batch 和学习率是否必须保持 |
| 确认点 2 | 估算完成后、运行冒烟测试前（阶段 B 结束） | 显存和硬盘的估算表；显存余量的建议值和理由；硬盘不够，或者预计占用超过剩余空间的一半时必须问 |
| 确认点 3 | 需要修改训练代码时 | 要加什么（显存测量、续训、参数入口）、加在哪个文件、对现有行为有什么影响 |
| 确认点 4 | 冒烟测试和调参都完成后（阶段 F） | 推荐配置、改了哪些参数及其类别、实测峰值和吞吐、实测后余量是否需要调整、预计训练时长和硬盘占用、续训验证结果；是否启动正式训练 |

提问的写法：

- 先用一两句直白的话说明发现了什么、为什么需要用户决定，再给 2–4 个选项，推荐项放第一个并说明理由。
- 有提问工具时优先使用，每轮最多问 4 个问题，一个问题只问一个决定。
- 能查清的事实先查清再问，不把调查工作推给用户；不问“是否继续？”这类含糊的问题。
- 与用户商议，尤其让用户选择时，不直接抛未经解释的函数名、配置键、缩写或参数速记，哪怕只有一个陌生名称也要解释。先说它是什么、做什么用、依据什么假设、为什么现在需要决定，再用完整句子讲清各选项的效果、代价、与项目已有约定的关系及是否需要额外授权。具体名称只作为核对信息，不能代替解释；选项标题和提问工具里的描述也遵守这条。
- 参数和数值要解释含义与单位。显存和速度收益有实测就给实测，没有就说明尚未验证；训练结果是否受影响、需要改哪些代码也要说明，不能为填满选项而编造结论。

以下仅示范沟通方式，假设项目已经支持梯度检查点且已实测；数字和结论不能直接套用到实际项目：

```text
反例：开 GC，peak 21.3/24G，tput -18%；备选 ZeRO-2。

正例：现在的设置下，显存峰值超出了我们商定的上限，正式训练中有爆显存的风险。有两种办法：
A. 打开梯度检查点（推荐）：训练时少存一部分中间结果，反向计算时重新算出。实测显存峰值为 21.3 GB，在 24 GB 的卡上剩余约 2.7 GB，满足我们商定的余量；代价是每秒处理的样本数下降约 18%。保留原来的训练方法，只需改项目已有的配置开关，并验证重算后的结果一致性。
B. 把优化器状态和梯度分到 4 张卡上分别保存（DeepSpeed 的 ZeRO 第 2 级）：让每张卡少存一部分模型状态，但会引入卡间通信，需要改启动命令和配置文件。如果项目原先约定不改训练框架，需要你额外授权；显存和速度收益尚未实测，不能承诺更快。
```

## 执行流程

按顺序执行 A 到 F 六个阶段，不能跳过。每个阶段完成后，在回复中简要说明结果。

### 阶段 A：了解项目和机器

1. 运行 `git status`、`git log --oneline -5`，了解工作区状态。
2. 读 AGENTS.md、CLAUDE.md、README，找出：训练入口、配置文件、使用的训练框架（纯 PyTorch、Lightning、HF Trainer、DeepSpeed 等）、产物目录规范、已有的续训功能。
3. 读训练入口和它调用的数据加载、模型构建、训练循环、保存加载代码，弄清：当前的每卡 batch、梯度累积、卡数、学习率和调度、精度、优化器、评估和保存的频率、样本长度或分辨率的分布。
4. 按“和 env-first 的关系”一节查清机器情况，用 `nvidia-smi` 看每张卡已被占用多少。
5. 到达确认点 1。

### 阶段 B：估算显存和硬盘

参考文件：**estimation.md（必须读）**。

1. 统计参数量：能运行代码时用 `sum(p.numel() for p in model.parameters())` 实际统计，不凭模型名称猜。
2. 按 estimation.md 估算权重、梯度、优化器状态占用，判断在目标卡上是否放得下，激活值留给冒烟测试实测。
3. 按 estimation.md 估算单个 checkpoint 大小和整个训练的硬盘总量，和 `df -h` 的剩余空间对比。
4. 按“显存目标”一节给出显存余量的建议值和理由。
5. 把结果整理成估算表，到达确认点 2。

### 阶段 C：冒烟测试

参考文件：**smoke-test.md（必须读）**；续训测试部分读 resume.md。

1. 第一级，跑通：少量步数走完前向、反向、优化器更新、评估、保存、加载。
2. 第二级，测峰值：用最坏情况的 batch，分别记录训练、评估、保存三个阶段的显存峰值。
3. 第三级，测吞吐：热身后计时，记录每秒样本数和 GPU 利用率。
4. 需要往训练代码里加测量代码时，先到达确认点 3。

### 阶段 D：调整参数

参考文件：**tuning.md（必须读）**。

目标是在显存目标以内让吞吐最高。每卡 batch 只是能调的东西之一，精度、梯度检查点、分片、数据加载同样要考虑。

1. 按 tuning.md 第二步先定精度等基础设置：项目没用混合精度、卡支持 bf16 时，把它作为首选推荐给用户（会改变训练结果，要问）。
2. 按第三步在当前设置下找每卡 batch：取峰值不超过显存目标、吞吐还在增长的最大值；吞吐不再增长时停止加大。
3. 显存限制了吞吐时（每卡 batch 为 1 也放不下，或者 batch 被显存卡住而吞吐还在涨），按第四步先分清显存主要花在固定占用还是激活值，再从轻到重加手段：梯度检查点 → 梯度累积（为了保持等效 batch）→ ZeRO/FSDP（多卡、单卡状态本身太大）→ offload（最后手段）。每加一项都实测峰值和吞吐，再回到第 2 步看 batch 能否加大；最终选显存目标以内吞吐最高的组合。
4. GPU 利用率偏低时，按第六步查数据加载。
5. 只影响速度和显存的参数自己调整并记录；会改变训练结果的参数，带着实测数据问用户。
6. 每次调整后重新测峰值，最终配置必须在最坏情况下实测过。

### 阶段 E：断点续训

参考文件：**resume.md（必须读）**。

1. 检查现有代码是否已经保存和恢复 resume.md 要求的全部内容；项目用了训练框架时，优先用框架自带的续训方式。
2. 缺少的部分，到达确认点 3 后再补。
3. 用冒烟测试测出的吞吐，把保存间隔换算成步数，写进配置。
4. 按 resume.md 做续训验证：连续训练和“中断再恢复”的结果要一致。
5. 用最终的保存频率和保留个数，重新核对硬盘预算。

### 阶段 F：最终报告

按下一节格式输出报告，然后到达确认点 4。用户确认前不启动正式训练。用户确认启动后，预计超过几分钟的训练放到后台（tmux 或 nohup），记下会话名或 PID 和日志位置。

## 完成前检查

报告完成前，逐条检查：

```text
- [ ] 确认点 1：训练入口、卡号、总步数、产物目录、可调整的参数已确认
- [ ] 关于机器的结论都有命令输出作为依据
```
