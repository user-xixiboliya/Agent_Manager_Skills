# Paper Explainer：先讲整体，再讲论文怎样改变它

## 触发与范围

- 只有用户在输入中显式调用 `/paper-explainer` 时，才启用本规范。
- 用户没有调用时，不因提到论文、公式或某个研究领域而自动启用；引用或讨论这个 skill 的名称也不算调用。
- 适用于任何领域的系统、方法、理论、实验或分析类论文，不限于 AI、世界模型或机器人。
- 用户只要求解释时，只阅读和讲解；调用本 skill 不授权修改代码、运行实验、安装依赖或下载额外资源。
- 用户在本轮明确指定讲解范围或深度时，以用户要求为准；不适用的框架项说明原因，不为填表编造组件或数据。

## 阅读与取证

1. 确认论文身份和版本，优先使用用户给的原文、附件或链接。未给出论文且无法唯一定位时，先询问；额外代码仓库、数据或实验资源需要用户提供或授权。
2. 先读问题设定、概览图、方法、基线和评估，再沿当前问题读相关公式、图表、附录。不能只靠摘要或二手介绍补全方法。
3. 关键说法给出出处：章节、页码、图表或公式编号；链接和编号必须真实核对。代码只说明所查版本的实现，不能直接当作论文定义。
4. 区分“原文明确说明”“由公式或实现推得”“为帮助理解的例子”“尚未确认”。无法访问正文或缺少证据时，说明讲解覆盖到哪里。
5. 作者报告的结果与已独立验证的结果分别表述；速度、精度等结论同时交代比较对象、测量条件和适用范围。

## 表达原则

- 用户能接受公式和代码，但需要先知道它们在整体流程中的角色；不给未经解释的专门名词、符号或代码变量。
- 先用日常语言讲功能，再附论文名称或代码名称。新名词首次出现解释含义、用途及关键假设；不能只把缩写展开成另一个陌生名称。
- 公式前说明它计算什么、谁调用、结果给谁用；公式中解释符号、单位、形状和索引含义，只展开与问题有关的数学细节。
- 向用户商议解释范围或提供选项时，先说功能是什么、为何需要决定，再说明各选项的实际效果、代价、原有约定和是否需要额外授权。具体名词只用作核对。
- 在报告、追问和纠错中继续使用已解释的直白叫法，不改成一串代码变量或自造简称。用户表示没懂时换一种说法或给例子，不以“已经解释过”带过。
- 段落连贯、长度适中；表格用于关系和比较，避免堆砌与问题无关的名词。

## 讲解顺序

默认采用“整体定位 → 组件角色与接口 → 基线瓶颈 → 论文改动与新旧对比 → 具体例子 → 一句话总结”。下面各部分按论文类型调整，始终先整体后细节。

### 整体定位：论文在哪个问题与流程里工作

先讲任务目标、输入、输出，以及结果怎样用于评估、决策或执行。即使领域中有默认流程，也要先解释，不能假设用户已知。

系统或方法类论文描述整体数据流：

```text
输入 → 处理或求解组件 → 结果 → 评估 / 决策 / 执行
```

这只是组织方式，实际组件和连线必须来自论文。训练流程和部署流程不同的，分开描述；反馈循环明确指出什么信息返回哪一步。

理论、实验或分析类论文说明“问题设定与假设 → 推导或实验设计 → 证据 → 结论”的关系，不强行改写成神经网络或控制系统。

给出核心组件角色表；理论或实验类可用研究环节代替软件组件：

| 组件或环节（直白名称） | 流程中的作用 | 谁提供输入、输入是什么 | 产生什么、谁消费输出 | 调用者与被调用者 |
|---|---|---|---|---|

### 接口与基线瓶颈：一次调用能完成什么

- 对关键旧组件先给单次输入输出契约：一次接受什么信息，返回什么结果，输入和输出粒度是什么。
- 分清上层想完成的整体任务与底层单次实际接受的输入。例如上层可能要整段结果，单次组件只处理一部分；具体关系需由原文证明。
- 说明完成整体任务怎样组织调用、哪些调用串行依赖，瓶颈发生在哪里；多次调用、误差累积或信息不足均须有依据，不能预设每篇论文都有这些问题。
- 分清一次组件调用、一次模型前向、一次求解迭代和一次完整任务；说明统计调用次数时包含哪些阶段。
- 如果论文没有软件调用接口，说明旧理论假设、实验设计或分析方法的限制；对应调用项标为“不适用”并解释原因。

### 论文改动：改在哪里，保留了什么

先明确整体流程是否改变、哪些组件保留，以及论文改变的是哪个接口、处理粒度、训练目标、损失函数、搜索策略、实验设计或评估方式。

每个新增或修改的关键组件，先写契约再讲内部：

```text
组件作用：它在整体流程中负责什么
输入：哪些数据、张量、状态或条件，由谁提供
输出：什么结果，粒度或形状是什么，由谁使用
关键约束：可见信息、因果关系、适用假设、资源或可行性限制
内部改动：怎样从输入得到输出，为什么针对前述瓶颈
```

只写实际适用的约束，不假定组件能看未来或只能看前若干步。介绍公式和伪代码前，再点明它属于哪一步。

### 新旧对比：用同一口径比较

至少覆盖以下项目；缺少原文依据的填“未说明”，不适用的解释原因。属于理论或实验论文的，用相应假设、研究设计和证据范围作对照。

| 对比项 | 基线 / 旧方法 | 论文方法 | 依据或说明 |
|---|---|---|---|
| 上层想查询或完成什么 | | | |
| 关键组件单次输入与输出 | | | |
| 完成一次整体任务需要调用几次 | | | |
| 中间结果是否依赖上一步预测或中间值 | | | |
| 训练或评估信号覆盖哪些部分 | | | |
| 速度、精度和误差累积的影响 | | | |

训练或评估信号的覆盖范围指哪些步骤、变量、输出或研究对象实际受到目标函数或评估指标约束。训练与推理、理论能力与实测结果分别比较，不混用运行时间或调用次数。

### 具体例子：沿数据流走一遍

整体和差异讲清后，再给简单输入、张量形状、向量例子或伪代码。例子用于理解，不冒充原文实验结果；同一例子尽量同时展示旧版和新版。

- 标清每次调用的输入、输出，以及哪些输出依赖前一次结果、哪些互相独立。
- 提到并行时，说明是计算图中可独立计算的分支、多设备计算，还是搜索中同时评估候选；可独立计算不等于已经实现并行或实测加速。
- 提到缓存、复用或一次前向时，说明缓存了什么、何时仍有效、省掉哪次重复计算，以及仍然需要做哪些计算。
- 形状和公式只展开解释数据流需要的部分，不用大段实现盖过方法逻辑。

### 一句话总结与纠错

方法类可用：“整体流程保留了……；论文把……组件的单次处理从……改为……，因此……。”理论或实验类说明改变的假设、研究设计或结论范围。

用户理解与原文或上一轮说法有矛盾时，主动指出冲突所在、给出依据和正确关系。自己上一轮讲错的，明确承认并修正；尚无法确认的部分保留不确定性。

## 调用示例

```text
/paper-explainer 请按整体流程、关键接口和新旧差异解释这篇论文：<论文链接或本地文件>
```

## 完成前检查

- [ ] 论文身份、已阅读范围和关键结论出处明确，未确认内容没有被说成事实
- [ ] 默认流程、组件角色及训练 / 部署或推导 / 实验关系已讲清
- [ ] 上层任务与单次接口分开说明，调用粒度和依赖没有混淆
- [ ] 每个关键改动先讲输入输出与约束，再讲内部公式或代码
- [ ] 新旧对比覆盖调用、依赖、信号范围和性能；缺失或不适用项如实说明
- [ ] 例子先有数据流，随后才有形状和伪代码；并行和复用含义明确
- [ ] 报告与追问没有未经解释的代码名词，前后矛盾已主动纠正
- [ ] 结尾用一句话收束，讲解没有擅自变成代码修改或实验执行
