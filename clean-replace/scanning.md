# 阶段 B、C：扫描整个项目并输出清单

> clean-replace 的参考文件。阶段 B 开始前读。

这是最关键的一步，也是最容易被跳过的一步。

## B.0 为什么不能只靠搜索名称

搜索只能找到“已经知道要搜什么”的内容。以下这些旧语义残留，靠搜索名称很容易漏掉：

- 同一个名称的其他写法，例如缩写、大小写不同、拼接字符串
- 动态引用，例如 `f"{name}_encoder"` 拼出来的类名
- 没有出现旧方法名称的描述，例如注释写“这里用残差连接保持梯度”
- 为旧方法写死的数值，例如输出维度 `2048`、输入尺寸 `224`、专门为旧方法调过的学习率
- 为旧方法设计的数据处理，例如只适合 CNN 的归一化方式
- 退回旧实现的 fallback

所以替换前必须**逐个文件阅读，判断每个文件是否与旧方案有关**。搜索只作为扫描后的交叉检查，不能代替阅读。

修改索引（见 change-index.md）可以帮助缩小必须阅读的范围，但不能代替核对。

## B.1 建立文件总表

列出项目中的所有文件，并按类型分类：

```bash
git ls-files
git ls-files --others --exclude-standard    # 未被跟踪、也未被忽略的文件
```

分类示例：

| 类型 | 示例 | 是否扫描 |
|---|---|---|
| 源代码 | `models/`、`algorithms/`、`utils/` | 扫描 |
| 入口脚本 | `train.py`、`eval.py`、`scripts/` | 扫描 |
| 配置 | `configs/`、`*.yaml` | 扫描 |
| 测试 | `tests/` | 扫描 |
| 当前文档 | `README.md`、`docs/`（不含修改索引的 `changes/`） | 扫描 |
| 项目说明文件 | AGENTS.md、CLAUDE.md | 扫描，修改前需用户确认 |
| notebook | `*.ipynb` | 扫描 |
| 构建和 CI 配置 | `pyproject.toml`、`Dockerfile`、`.github/` | 扫描 |
| 第三方代码 | `externals/` | 扫描并列出，默认不修改 |
| 历史文档 | CHANGELOG、实验记录、修改索引中的修改记录 | 不扫描，只追加 |
| 实验产物 | 结果、日志、权重 | 不扫描，只记录 |

## B.2 用修改索引确定阅读范围

**阅读前先读：**

- AGENTS.md、CLAUDE.md 等项目说明文件
- 从中获取模块划分和项目约定，作为确定扫描范围的参考，但不能代替阅读具体文件

然后按以下规则，把每个需要扫描的文件分成“必须阅读”和“可以跳过”两类。

**必须阅读：**

1. 修改索引中，与旧实现相关的修改记录涉及的文件
2. 文件职责表中，“涉及的方法或概念”包含旧方案的文件
3. 文件职责表中没有记录的文件
4. 文件职责表中有记录，但当前内容哈希与记录不一致的文件
5. Git 历史中与旧方案有关的文件：

   ```bash
   git log -S'ResNetEncoder' --name-only --format=''   # 引入或删除过该名称的提交
   ```

6. 从入口脚本出发，沿调用链经过的所有文件
7. 交叉检查中搜索命中的文件，见 B.5

**可以跳过：**

同时满足以下条件的文件可以跳过：

- 文件职责表中有记录
- 当前内容哈希与记录一致
- 记录的职责和概念与本次替换明显无关

跳过的文件要在扫描覆盖报告中列出，并说明原因。

**没有修改索引时：**

- 必须阅读所有需要扫描的文件。
- 扫描完成后，用扫描结果建立文件职责表。

**需要阅读的文件超过 100 个时：**

不论有没有修改索引，需要阅读的文件超过 100 个时，先告诉用户再开始阅读；不超过 100 个就直接读。

这里的“需要阅读的文件”只包括代码、配置、测试、脚本和文档，不包括实验产物、第三方代码和历史文档。

告诉用户时说明：

- 需要阅读的文件数量，按类型分列
- 为什么需要读这么多，例如“项目中还没有修改索引”
- 预计耗时

可选处理方式：

- A. 全部读完再输出清单（推荐）
- B. 分批阅读，每读完一个模块汇报一次
- C. 先暂停

不能以“文件太多”为理由，自行跳过没有索引记录的文件。

## B.3 逐个阅读，并逐个判断

对每个必须阅读的文件：

- 阅读整个文件，而不是只看搜索命中的那几行。
- 阅读时检查：
  - 显式引用：import、类名、函数名
  - 动态引用：注册名、字符串拼接、`getattr`、配置中的类路径
  - 为旧方法写死的数值和形状
  - 为旧方法设计的数据处理和参数
  - 描述旧行为的注释、docstring 和文档段落
  - 退回旧实现或其他静默兜底的 fallback
  - 断言旧行为的测试
  - 指向旧方法的默认值
- 给每个文件一个结论：
  - 修改
  - 删除
  - 无关
- 读完后更新阶段 A 的旧标识清单，补充新发现的名称和写法。

## B.4 追踪调用关系

- **向上查**：谁调用了旧实现？这些调用方都要修改。
- **向下查**：旧实现使用了哪些辅助函数、工具类、常量？这些内容是否还有其他使用者？只被旧实现使用的，要一起删除。
- **从入口查**：从训练、评估、推理、命令行入口出发，走一遍实际运行路径，确认每条路径最终使用的都是新实现。

## B.5 用搜索做交叉检查

扫描完成后，用补充后的旧标识清单搜索整个仓库：

```bash
git grep -n -i -E '<所有旧标识，用 | 连接>'
```

检查每个命中项：

- **命中的文件已经阅读，并判定为修改或删除**：正常。
- **命中的文件被判定为“无关”**：判断可能有误，需要重新阅读。
- **命中的文件之前跳过或没有阅读**：扫描范围有漏洞，必须补读。
  - 如果这个文件是根据修改索引跳过的，说明索引记录不准确，要在阶段 F 中修正索引。

## B.6 判断是否有外部调用方

检查旧接口是否可能被当前仓库以外的地方使用，例如：

- 作为包发布
- 在 `__all__` 中公开导出
- 被其他仓库、服务、脚本或 notebook 引用
- 文档中写明供外部使用

只要存在这种可能，就在确认点 2 中询问用户，不要自行判断。

## B.7 输出扫描覆盖报告

扫描覆盖报告随确认点 2 一起提交给用户：

```text
## 扫描覆盖
- 文件总数：182
- 需要扫描：96（不含第三方代码 40、历史文档 3、实验产物 43）
- 已阅读：31
  - 其中修改索引指向 8 个，调用链涉及 12 个，没有索引记录或内容已变化 9 个，交叉检查补读 2 个
- 根据修改索引跳过：65（内容哈希与记录一致，职责与本次替换无关，明细见附表）
- 交叉检查：旧标识命中 14 处，全部位于已阅读文件中
- 修改索引不准确的地方：2 处（将在阶段 F 中修正）
```

## 阶段 C 的清单格式

### C.1 清单格式

先用两三句话直白说明影响范围，再给出详细表格。

示例：

```text
这次替换会影响训练、评估和文档三部分，共 10 个文件：
- 修改 7 个
- 删除 2 个
- 第三方代码 1 处，默认不修改
另外有 1 处可能被外部使用，有 2 处 fallback 需要你决定是否删除。
```

然后输出：

```text
## 受影响文件清单
| # | 文件 | 发现的内容 | 计划处理方式 | 需要你决定 |
|---|---|---|---|---|
| 1 | models/encoder.py | ResNetEncoder 定义 | 修改：替换为 ViTEncoder | |
| 2 | models/blocks.py | ResNetBlock，只被 ResNetEncoder 使用 | 删除 | |
| 3 | models/__init__.py | 公开导出 ResNetEncoder | 修改 | 是否有外部代码 import 它？ |
| 4 | registry.py | register("resnet")；查不到注册名时退回 ResNetEncoder | 修改，并删除 fallback | |
| 5 | configs/default.yaml | encoder: resnet、resnet_depth | 修改 | |
| 6 | configs/resnet50.yaml | 整个文件属于旧方案 | 删除 | |
| 7 | eval.py | 通过注册名 "resnet" 加载模型 | 修改 | |
| 8 | tests/test_encoder.py | 测试 ResNet 输出形状 | 修改：改为测试 ViT | |
| 9 | README.md、docs/method.md | ResNet 和残差结构说明 | 修改 | |
| 10 | AGENTS.md | 写着“encoder 使用 ResNet” | 修改（需要你确认） | 是否同步更新？ |
| 11 | externals/xxx/ | 第三方代码中的 resnet | 不修改 | 是否需要一起修改？ |
```

### C.2 同时提交给用户确认的内容

- **扫描覆盖报告**
  - 格式见 B.7。

- **项目中已有的 fallback**
  - 按 rules.md 中“fallback 层面”末尾的格式列出位置、触发条件、触发后走的路径和默认建议。

- **新名称**
  - 如果有多个合理选项，列出选项和推荐理由。

- **CHANGELOG 条目草稿**
  - 按项目现有格式写好。

- **实验记录条目草稿**
  - 按项目现有格式写好。
  - 实验结论和数字只能来自用户说明或真实的结果文件。
  - 缺少依据的部分留空，并询问用户，不能编造。

- **本次替换会产生的实验产物**
  - 如果后续要运行实验，说明产物会放到哪个目录。
