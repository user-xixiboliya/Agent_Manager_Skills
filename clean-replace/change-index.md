# 修改索引

> clean-replace 的参考文件。阶段 A 确定位置、阶段 B 确定阅读范围、阶段 F 更新索引时读。

## 作用

修改索引是给 agent 使用的项目记录，主要解决两个问题：

1. **缩小扫描范围**
   - 根据过去的修改记录，快速找到与某个方法有关的文件。

2. **记录每个文件的职责**
   - 文件内容没有变化、职责也和本次替换无关时，可以跳过阅读，不必每次都扫描整个项目。

修改索引只帮助缩小范围，不能代替核对。

- 文件内容已经变化时，必须重新阅读。
- 交叉检查发现遗漏时，必须修正索引。

## 与其他文档的区别

| 文档 | 给谁看 | 记录什么 |
|---|---|---|
| CHANGELOG | 人 | 宏观上怎么变的，几句话 |
| 实验记录 | 人 | 跟进实验：设置、结果、结论，当前有效的是哪一套结果 |
| 修改索引 | agent，也方便人查阅 | 每次修改了哪些文件、各改了什么，以及每个文件的职责 |

修改记录不写替换原因和实验结论，写一句“原因见 CHANGELOG 某日条目”。分工见 records.md。

## 位置和结构

默认放在 `docs/agent-index/`。如果项目已有约定，以项目约定为准，例如 AGENTS.md 或 CLAUDE.md 中指定了其他位置。

```text
docs/agent-index/
  file-map.md                      # 文件职责表，每个文件一行
  changes/
    2026-10-08-resnet-to-vit.md    # 每次更新一份修改记录
```

要求：

- 修改索引应纳入 Git 管理，不要放进 `.gitignore`。
- 第一次创建 `docs/agent-index/` 时，在确认点 1 中告诉用户并确认。

## 修改记录格式

每次更新写一份，保持简短。每个文件只写一行。

```text
# ResNet 编码器替换为 ViT

- 日期：2026-10-08
- 任务：/clean-replace ResNet 编码器实验效果不好，换成 ViT
- 替换关系：ResNetEncoder → ViTEncoder
- 原因：见 CHANGELOG 2026-10-08 条目
- 涉及概念：encoder、ResNet、ViT
- 开始时的 commit：abc1234

## 修改文件
| 文件 | 操作 | 简要内容 |
|---|---|---|
| models/encoder.py | 修改 | ResNetEncoder 替换为 ViTEncoder，输出维度保持 512 |
| models/blocks.py | 删除 | ResNetBlock 只服务于 ResNet |
| registry.py | 修改 | 注册名从 "resnet" 改为 "vit"；删除查不到时退回 ResNet 的 fallback |
| eval.py | 修改 | 通过注册名加载 encoder，改用 "vit" |
| configs/resnet50.yaml | 删除 | ResNet 专属配置 |

## 扫描覆盖
- 阅读 31 个，根据索引跳过 65 个

## 下次修改时注意
- eval.py 通过注册名动态加载 encoder，搜索类名时找不到它
```

“下次修改时注意”只写本次扫描中发现的、容易遗漏的地方。没有就不写。

## 文件职责表格式

```text
| 文件 | 职责 | 涉及的方法或概念 | 内容哈希 |
|---|---|---|---|
| models/encoder.py | 图像编码器定义 | encoder、ViT | 3f2a9c1e |
| registry.py | 模型注册表，按字符串名构建模型 | encoder、注册名 | 77b0d4a2 |
| utils/logging.py | 日志工具 | 无 | 9e81c0f3 |
```

要求：

- 每个文件只写一行。
- 职责写这个文件负责什么，不写修改历史。
- “涉及的方法或概念”写当前内容中出现的方法名和关键概念，用来判断它与某次替换是否有关。
- 内容哈希使用 Git 的内容哈希，取前 8 位。文件没有提交时也可以计算。

计算单个文件的内容哈希：

```bash
git hash-object models/encoder.py | cut -c1-8
```

批量对比当前哈希与职责表：

```bash
git ls-files | while read f; do echo "$(git hash-object "$f" | cut -c1-8) $f"; done
```

## 使用规则

- 哈希不一致，说明文件在上次核对后被人或其他 agent 修改过，必须重新阅读。
- 职责表中没有的文件，必须阅读。
- 只写读过、核对过的事实，不根据文件名推测职责。
- 修改记录是历史文档，不改写已有内容；其中出现旧标识是正常的，属于 G.1 的白名单。
- 文件职责表描述当前状态，每次扫描后都要更新；其中不应出现已被替换的旧方案。

## 与 AGENTS.md、CLAUDE.md 的关系

项目中的 AGENTS.md、CLAUDE.md 等 agent 说明文件，通常已经写了部分文件和模块的职责，以及项目约定。

两者分工不同：

| 文件 | 内容 | 维护方式 |
|---|---|---|
| AGENTS.md、CLAUDE.md | 项目约定，以及模块级的职责说明 | 主要由用户维护 |
| `file-map.md` | 每个文件的职责、涉及的方法或概念、内容哈希 | 由 agent 每次扫描后维护 |

### 使用顺序

1. 阶段 A 先读 AGENTS.md 和 CLAUDE.md，获取：
   - 项目约定
   - 模块划分
   - 产物目录
   - 修改索引位置等规则
2. 建立或更新 `file-map.md` 时，可以参考其中的职责描述，但必须以实际读过的文件内容为准。
3. 不把 AGENTS.md 和 CLAUDE.md 的内容整段复制进 `file-map.md`，避免两处内容不一致。
   - 需要时，可以在职责栏中写“见 AGENTS.md 中的某一节”。

### 发现不一致时

如果 AGENTS.md 或 CLAUDE.md 中的描述与实际代码不一致，例如说明里写“encoder 使用 ResNet”，但代码已经换成 ViT：

- 不擅自修改，在确认点 2 中列出不一致的位置，询问用户是否更新。
- 这些文件是用户维护的规则文件，即使只是同步描述，也要先确认。

### 本次替换导致说明过时

如果本次替换会让 AGENTS.md 或 CLAUDE.md 中的描述过时：

- 把这些文件列入受影响文件清单。
- 处理方式标为“修改（需要你确认）”。

## 阶段 F：更新修改索引

在 CHANGELOG 和实验记录之后，更新修改索引：

1. 在 `changes/` 中新增本次修改记录，格式见上文“修改记录格式”。
2. 更新文件职责表：
   - 本次阅读过的文件：更新职责、涉及的方法或概念、内容哈希。不论是否修改，都要更新。
   - 删除的文件：删除对应行。
   - 新增的文件：添加对应行。
   - B.5 中发现记录不准确的行：修正。
3. 内容哈希必须在所有修改完成后计算，不能用修改前的哈希。
