# 记录、证据和归档

> clean-replace 的参考文件。阶段 A 读；写 CHANGELOG、实验记录、修改索引，生成证据或打包交付，整理堆积的版本和记录时对照执行。

记录越多不等于越清楚。同一件事写在五六个地方、版本一层叠一层、正文里手抄哈希，结果是改一处就要改好几处，漏改一处就会口径对不上，最后谁也说不清现在用的是哪一套。

## 三份记录的分工

| 文档 | 给谁看 | 写什么 | 不写什么 |
|---|---|---|---|
| `changes/` 修改记录 | agent | 改了哪些文件、各改了什么，方便追溯 | 替换原因、实验结论 |
| CHANGELOG | 人 | 宏观上怎么变的，几句话 | 文件清单、实验数字 |
| 实验记录 | 人 | 跟进实验：设置、结果、结论；当前有效的是哪一套结果，哪些作废了、为什么 | 文件清单 |

最终报告是对话中的回复，不存进项目，可以引用这三份记录。

## 同一件事只写一处

- 每件事选一个地方写，其他地方引用它，例如“原因见 CHANGELOG 2026-10-08 条目”“当前结果见实验记录某一节”。
- 新建记录文件之前，先说明谁会读它：代码会读取，或者项目规范要求有这个文件。说不出读取方的，不新建，写进已有的记录。
- 不把同一段历史抄进 README、docs、说明文档和多份 JSON。
- 发现项目里已有的重复记录时，不擅自合并，在报告中列出：哪几处重复、哪一处被代码读取、建议保留哪一处。

## 当前有效的结果写在实验记录里

- 多套结果并存时（例如重跑过几轮、换过 Reference），在实验记录中写清：当前有效的是哪一套、路径在哪里；哪些已经作废、作废原因。
- 作废的结果不移动、不改名、不删除，由用户决定怎么处理。
- 不建“指针目录”或用相对路径（`../../../`）指向别处的文件来表示当前版本，目录一移动就失效。
- 目录名不加 `current`、`latest`、`v3` 这类状态词，见 rules.md 中的命名规范。

## 状态类文件直接改成当前值

决策文件、状态 JSON、配置这类“记录现在是什么”的文件：

- 直接覆盖成当前值，顶层就是当前结论。
- 不追加 `revision_xxx` 层，不保留过时的 `status` 字段。
- 改了什么、为什么改，在实验记录（或 CHANGELOG）中写一行。

历史文档（CHANGELOG、实验记录、`changes/`）的规则不变：只追加新条目，不改写已有条目。

## 哈希、镜像和版本

- **只做必要的校验**：项目规范要求的（例如结果中记录方法哈希、checkpoint 哈希和权重文件一致、reload 后指标一致），以及评分或安全相关的防篡改检查。
- **哈希由程序生成**，写进机器读取的文件，例如运行记录、`artifact.json`、lock 文件。
- **文档里不手抄哈希或 digest**。文档写名称，再写“具体版本见某个文件”，例如：`基础镜像：pg-antmaze-env，具体版本见 runs/xxx/artifact.json`。
- 不做规范没要求的校验：每次运行前 `sha256sum -c`、每个归档目录单独生成 `SHA256SUMS`、为了记录一个会被反复修改的文件的哈希而另存一份启动快照。
- **镜像标签用过就不再复用**：每次重新构建用新标签。文档不依赖 `dev`、`latest` 这类会被挪走的标签。

## 不搭建规范没要求的机制

- 不为一次运行生成规范没要求的控制文件，例如 GO、ready、receipt、status 一堆小文件。
- 需要监控（GPU、内存）时，先问用户记录频率和保存位置，不默认每秒记一行。
- 已有证据引用了这类文件时，不删除，在报告中说明。

## 打包交付按白名单

- 只放规范要求的文件，逐项列出，不整个目录打包。
- 打包前检查没有缓存混进来：`.nv/`、`ComputeCache`、`__pycache__`、`*.pyc`、`.cache/`，以及容器把 HOME 指到产物目录后留下的 `home/` 目录。
- 校验文件（如 `SHA256SUMS`）只覆盖白名单中的文件。

## 临时文件放在 `.agents/tmp/`

- agent 写的一次性脚本、调试脚本、诊断输出，放在项目根目录的 `.agents/tmp/`，不放进源码目录、证据目录或产物目录。
- 第一次创建时，把 `.agents/tmp/` 加进 `.gitignore`，并告诉用户。
- 任务结束时，在最终报告中列出 `.agents/tmp/` 里的文件，用户确认后再删除。
- 正式实验的结果、日志、权重不放在这里，按 artifacts.md 处理。

## 整理已经堆积的项目

用户要求整理一个版本多、记录重复、缓存多的项目时：

1. **先写报告，不动文件**。按类别列出问题：
   - 版本太多
   - 同一件事记了多遍
   - 哪些校验必要、哪些多余
   - 过期文件和垃圾
   - 超出规范的机制

   每项写路径、大小、被谁引用，最后给出整理顺序。
2. **按风险从低到高整理**：
   1. 清理纯垃圾
   2. 合并记录
   3. 归档瘦身
   4. 重新生成交付文件
3. **删除前先找引用**：用 `grep -rn` 找出所有引用要删除内容的文档和代码，先改引用，再删除。
4. **删除的分工**：
   - 纯垃圾由 agent 删除，用户确认清单后才删。纯垃圾包括：编译缓存（`.nv/ComputeCache`）、`__pycache__`、`*.pyc`、`.agents/tmp/` 里的临时脚本。
   - 容器留下的 `home/` 目录不整个删：只删其中确定是缓存的子目录（如 `.nv/`、`__pycache__`）。删完后 `home/` 空了就删掉这个空目录；还剩别的东西（例如 `.cache/torch/hub` 里的权重、配置、日志、程序写到 `~` 下的结果），列给用户决定。
   - 实验结果、日志、权重、数据由用户删除，agent 只给出清单和命令。
5. **删完核实**：用 `ls`、`find` 确认确实删掉了，不只看删除工具的返回信息。
6. **有别的会话在改同一批文件时先停下**：用户说明有别的会话在改，或者发现文件在自己没动的情况下变了，就停下来告诉用户，等那个会话停了，再由一个会话统一整理。
