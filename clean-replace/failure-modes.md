# agent 为什么会越改越乱

> clean-replace 的参考文件。调用 /clean-replace 后先读一遍，开始前对照检查。

替换任务出问题，通常不是因为不会写新代码，而是因为下面这些习惯。开始前先对照检查。

## 增量思维：只加不删

**表现**：新实现写好以后，旧实现原封不动留着，觉得“留着也没坏处”。

**后果**：项目里出现两个都能用的同类实现。下一次修改时，agent 或人不知道哪个才是当前方案，可能改错地方，甚至把旧方案重新接回来。

**要求**：新代码写好时，替换只完成了一半；旧代码删掉、引用改完，才算完成。

## 局部视野：只改看到的文件

**表现**：只修改当前打开的文件、报错的文件、主入口文件，或者只修改搜索名称命中的文件。没有被直接 import、但通过配置、注册名、字符串引用的文件被漏掉；没有出现旧名称、但仍按旧方法写死的代码也被漏掉。

**后果**：A、C、D、F、G 改了，B、E 还停留在旧方案。代码能跑，但某条路径仍在调用旧逻辑，或者文档仍在描述旧方案。之后再查时才发现语义不对，是旧版本的。

**要求**：修改前逐个文件扫描项目（阶段 B），列出完整的受影响文件清单，经用户确认后再开始修改。搜索只用来交叉检查，不能代替阅读。

## 风险回避：不敢删，就改成备份

**表现**：担心删错，把旧文件改名为 `_bak`，移进 `archive/`，或者把旧代码注释掉。

**后果**：搜索时旧代码和新代码一起出现。读代码的人分不清哪些仍然有效，项目也越来越臃肿。

**要求**：Git 历史已经保存了旧版本。删除受 Git 跟踪的代码不会丢失历史，不需要在工作区再保留一份。真正担心的是删错，所以用确认点 2 让用户把关，而不是用备份文件代替判断。

## 版本命名：用后缀区分新旧

**表现**：新实现命名为 `EncoderV2`、`train_new.py`、`improved_loss`。

**后果**：“V2”只说明它比别的版本新，不说明它是什么。下次再替换就会出现 V3、`new_new`，名字越来越难读。

**要求**：按“它是什么”命名，不按“它是第几版”命名。

## 文档漂移：代码改了，说明没改

**表现**：代码已经换成新方法，但 README、docstring、注释、参数说明、运行命令还在描述旧方法。

**后果**：之后读文档的人或 agent 会按旧方法理解代码，甚至按文档把旧方法改回来。

**要求**：所有描述当前行为的文本，都属于这次替换的修改范围。

## 兼容焦虑：为了不破坏，加转发层

**表现**：旧函数保留，只是在里面调用新函数；或者增加 `use_legacy=True` 开关。

**后果**：旧名称以“兼容”的名义保留下来，后续代码仍会继续使用旧名称。新旧两套语义长期并存。

**要求**：内部代码直接改调用方。是否存在外部调用方由用户判断，不确定时一律询问。

## 产物散落：结果到处放

**表现**：日志写到项目根目录，权重存在另一个目录，结果放在第三个目录，或者给旧结果目录随手加 `_old` 后缀。

**后果**：用户找不到某次实验的完整记录，也分不清哪些结果对应哪个方法，难以管理和清理。

**要求**：实验产物按统一结构存放，按方法命名，agent 不删除、不移动、不重命名已有产物。详见 artifacts.md。

## 自作主张：细节靠猜

这是最需要防范的问题，因为猜错的结果通常不会立刻暴露。

agent 猜了一个方案并继续做下去，代码能跑、测试能过，报告写的也是“已完成”。用户会以为每个细节都经过确认，直到几天后实验结果不对、语义混乱，才发现某个地方是 agent 自己猜的。那时返工，还要先把猜测找出来，成本远高于当初问一句。

### 常见的猜测

| 类别 | agent 常见的猜测 | 后果 | 正确做法 |
|---|---|---|---|
| 替换范围 | 把“换掉 encoder”理解为只换网络，不动预处理；或者反过来，把相关流程全改了 | 少改留下旧语义，多改破坏无关功能 | 在 A.2 写清范围，并在确认点 1 确认 |
| 用户意图 | 把“这个方法不好”理解为删掉，而用户其实想调参 | 删掉了用户还要用的东西 | 意图不明确时先问 |
| 新方法参数 | 新方法的超参数随手取值，或者沿用旧方法的超参数 | 实验结果不可信，用户以为参数有依据 | 参数来自论文、官方代码或用户；没有来源就问 |
| 对外行为 | 新实现输出维度变了，自己去改下游模块适配 | 修改范围悄悄扩大 | 行为变化必须在确认点 2 或 3 说明 |
| 命名 | 自己选一个新名字 | 与用户习惯或后续计划不一致 | 有多个合理选项时让用户选 |
| 代码用途 | “这个函数看起来没人用”就删；“这个可能有用”就留 | 误删，或者留下旧语义 | 先扫描确认；查不清就问 |
| 测试失败 | 测试失败就改测试，让它通过 | 掩盖新实现的 bug | 判断不了原因就问 |
| 实验信息 | 编造或估计实验数字和结论，写进实验记录 | 实验记录失真 | 只写有依据的内容，缺少依据就留空并问 |
| 运行环境 | 自行假设 GPU、数据路径、依赖版本 | 换了环境就出错，或者静默走另一条路径 | 查配置；查不到就问 |
| 兼容需求 | 担心破坏现有功能，自己加 fallback 或兼容层 | 旧语义保留下来，问题被掩盖 | 不加；用户明确要求时才加 |
| 第三方代码 | 觉得需要，就顺手修改第三方代码 | 改了不该改的代码 | 用户确认后才修改 |
| 历史决定 | 根据旧代码或早期对话，推测用户现在的偏好 | 用过时的判断指导当前修改 | 以本轮确认为准 |

如何识别自己在猜、哪些可以自己决定、两条硬性要求，见 SKILL.md 中的“不要猜”。

## 静默 fallback：失败时偷偷走另一条路

**表现**：新实现出错、依赖缺失或配置没写时，代码不报错，而是自动改用旧实现、默认值或另一条路径。

```python
try:
    encoder = ViTEncoder(cfg)
except Exception:
    encoder = ResNetEncoder(cfg)        # 新实现失败，静默改用旧实现
```

```python
name = cfg.get("encoder", "resnet")     # 配置没写时，默认使用旧方法
```

**为什么 agent 喜欢这样写**：它想让代码“更健壮”、让测试通过、避免程序崩溃。

**后果**：

- 新方法可能根本没有生效，但程序看起来正常运行
- 实验结果混进了旧方法，结论不可信
- 真正的问题被掩盖，之后很难定位
- 旧实现因为“还在被 fallback 使用”而一直删不掉

**要求：从源头处理，写代码时就不写 fallback**

- agent 在本次任务中写的所有代码，都不能包含 fallback，包括新实现、调用方、配置读取、测试和脚本。
- 出错时直接报错，并给出清楚的错误信息，例如期望的配置项、文件路径或依赖名称。
- 如果 agent 认为某处确实需要 fallback，必须先问用户，不能先写上再报告。
- 提问时说明：
  - 不写 fallback 时，会在什么情况下报错
  - 写了 fallback 后，可能掩盖什么问题
- 默认建议用户不写 fallback。
- 用户明确同意后才能写。写入的 fallback 必须满足：
  - 触发时输出明确的日志或警告
  - 在最终报告中列出 fallback 的位置和触发条件
