# 与用户确认的方式

> clean-replace 的参考文件。调用 /clean-replace 后先读一遍；每次向用户提问前对照执行。

## 什么时候要问

除四个确认点外，遇到以下细节时也要问，不要自己猜（判断方法见 SKILL.md 中的“不要猜”）：

- 新实现叫什么名字，有多个合理选项时
- 新方法的参数没有来源时
- 某个辅助函数、配置项是否只服务于旧方案，查不清时
- 新旧方案的对外行为不同，例如输出维度、返回格式、默认值变化
- 旧接口是否有外部调用方
- 是否需要修改第三方代码
- 某处是否需要 fallback（默认建议不写）
- AGENTS.md、CLAUDE.md 的描述是否需要更新
- 需要阅读的文件超过 100 个时，是否继续
- 测试失败的原因无法判断时
- 实验产物放在哪里，目标目录已存在时怎么办
- CHANGELOG 和实验记录写什么，尤其是实验结论
- 是否提交 commit

## 什么时候不要问

- 读代码、跑搜索就能查清的事实，先查清再说结论，不要把调查工作推给用户。
- 本规范已经规定了做法的事，例如“不用 v2 命名”“不写 fallback”，直接照做。
- 不问含糊的问题，例如“是否继续？”“这样可以吗？”。

## 一般提问格式

每个问题都按以下顺序表达：

1. **背景**
   - 用一两句话说明发现了什么，为什么需要用户决定。

2. **选项**
   - 给出 2 到 4 个选项。
   - 每个选项说明选择后会发生什么。

3. **推荐**
   - 推荐项放在第一个，并说明推荐理由。

有提问工具时，例如 `AskUserQuestion`，优先使用提问工具。

每轮最多问 4 个问题。问题多时：

- 按重要程度排序
- 分批提问
- 一个问题只问一个决定

## 项目名称较多时，先直白解释

一个问题中如果不得不出现 5 个以上项目内的具体名称，例如文件名、类名、函数名、配置键、缩写，就不能直接把名称堆给用户。

必须按以下顺序表达：

1. 先不用这些名称，直白说明这个问题在讲什么、影响什么。
2. 再给出选项，选项也用直白语言描述。
3. 最后单独列出涉及的具体名称，方便用户核对。

**反例：直接堆名称**

```text
是否删除 build_resnet、ResNetBlock、_load_pretrained、RESNET_URLS、resnet_depth、width_multiplier？
```

**正例：先解释，再选择，最后列名称**

```text
旧的 ResNet 编码器有一批配套代码，只给它自己用。
这些代码包括：搭网络结构的部件、下载预训练权重的函数和地址表，以及两个只对 ResNet 有意义的配置参数。
换成 ViT 后，这些内容都用不上了。我已经检查过，项目中没有其他代码使用它们。

选项：
A. 全部删除（推荐）：项目中只留下 ViT 相关代码；需要时可以从 Git 历史找回。
B. 保留预训练权重下载函数，其余删除：如果你之后还想下载其他预训练模型，可以选这个。
C. 全部保留：这些代码会继续以未使用状态留在项目中，不推荐。

涉及的具体名称：
- 网络部件：build_resnet、ResNetBlock
- 权重下载：_load_pretrained、RESNET_URLS
- 配置参数：resnet_depth、width_multiplier
```

## 名称少于 5 个时

可以直接提到名称，但仍然要说清楚：

- 这是什么
- 为什么需要用户决定
- 每个选项会带来什么结果

**正例**

```text
`models/__init__.py` 把 `ResNetEncoder` 公开导出。
如果你的其他仓库或 notebook 直接 import 了它，删除后那些代码会报错。

选项：
A. 直接删除（推荐，适用于只有本项目使用的情况）
B. 先暂停，你确认外部引用情况后再继续
```
