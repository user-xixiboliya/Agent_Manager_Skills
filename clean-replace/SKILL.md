## 触发与范围

### 触发规则

- 只有用户在输入中显式调用 `/clean-replace` 时，才启用本规范。
- 用户没有调用时，不主动套用本规范，即使任务看起来像重构或替换。
- 一旦调用，本规范在本轮任务内全程有效，直到最终报告完成。

### 适用场景

- 某个方法经过实验验证效果不好，要换成另一个方法
- 某个网络结构、损失函数、优化器、采样策略要整体替换
- 某个接口签名、数据格式、配置结构要改成新的形式
- 前几轮修改留下了新旧并存的实现，需要统一收口

### 不适用场景

- 用户明确要求新旧方法并存，用来做对比实验
- 用户明确要求保留旧接口，给外部调用方过渡
- 只是新增一个独立功能，不涉及替换已有功能

用户在本轮的明确要求与本规范冲突时，以用户要求为准，并在最终报告中写明。

### 确认点

整个流程中有四个确认点。到达确认点时，必须停下来等用户回复，不能自行继续。

| 确认点 | 时机 | 需要确认的内容 |
|---|---|---|
| 确认点 1 | 开始修改前 | 替换关系（A.2）、工作区状态、是否先提交回退点、修改索引的位置（首次创建时）、替换范围中的歧义、缺失的项目约定 |
| 确认点 2 | 扫描完成、输出清单后（**必须停下**） | 扫描覆盖情况、修改范围、删除项、项目中已有的 fallback、AGENTS.md / CLAUDE.md 中需要更新的描述、外部调用方、第三方代码、CHANGELOG 和实验记录条目 |
| 确认点 3 | 执行中出现清单外的情况 | 新发现的受影响文件、测试失败原因不明、行为变化超出预期、替换关系需要调整、认为某处需要 fallback |
| 确认点 4 | 全部完成后 | 是否提交 commit、实验产物如何处理 |

此外，阶段 B 中需要阅读的文件超过 100 个时，先告诉用户再继续。

## 核心原则

### 原则一：同一个职责只有一个当前实现

同一项任务，例如“提取图像特征”“计算 critic loss”“加载数据集”，项目中只能有一个当前实现。

判断方法：如果有人问“这个项目用什么方法做 X”，代码中只能找到一个答案，不能出现“有时用 A，有时用 B，取决于某个旧配置”。

### 原则二：替换就是新增新实现，同时删除旧实现

新增新实现、删除旧实现，是同一个任务的两个部分，不能只做一半。不能先写新实现，并把删除旧实现留到以后，因为“以后”通常不会发生。

### 原则三：Git 历史就是代码归档

旧方案的完整代码保存在 Git 历史中，需要时可以通过 `git log`、`git show`、`git checkout <commit> -- <path>` 找回。因此工作区里不需要，也不允许出现任何形式的旧代码备份。

### 原则四：代码和项目文档只描述当前状态，历史写进专门文档

- 代码、配置、测试、README、docs 只描述“现在怎么做”。
- “以前怎么做、为什么改、实验结论是什么”写进项目的 CHANGELOG 和实验记录文档。
- “每次改了哪些文件”写进修改索引的修改记录。
- 这些本来就是历史文档，其中出现旧方法名称是正常的，不属于旧语义残留。

### 原则五：只做替换相关的修改

本规范要求彻底清理旧方案，但不允许借机重构无关代码。只修改：

- 旧实现本身
- 旧实现的引用
- 只服务于旧实现的辅助代码
- 描述旧实现的文档
- CHANGELOG、实验记录和修改索引中的新增条目

与本次替换无关的代码，即使看起来可以优化，也不要修改；可以在最终报告的“建议”中提出。

### 原则六：细节交给用户判断

agent 负责调查清楚，再给出选项和建议；用户负责做决定。不要用自己的猜测替代用户的判断，也不要把没有调查过的问题直接丢给用户。具体见下一节“不要猜”。

### 原则七：失败要显式，不写静默兜底

写代码时，出错就直接报错，让问题暴露出来，不要悄悄换一条路径继续运行。这条规则适用于所有静默兜底，不只限于退回旧实现：

- 退回默认值
- GPU 不可用时退回 CPU
- 找不到权重时改用随机初始化
- 找不到数据时改用合成数据
- 捕获异常后返回空值或零值

agent 认为确实需要 fallback 时，先问用户；用户同意后才写，并且触发时必须输出明确的日志或警告。原因和例子见 failure-modes.md 中的“静默 fallback”，禁止写法见 rules.md 中的“fallback 层面”。

## 不要猜

猜错的结果通常不会立刻暴露：代码能跑、测试能过，用户会以为每个细节都确认过，直到实验结果不对才发现。常见的猜测见 failure-modes.md 中的“自作主张”。

### 识别自己正在猜测

出现以下情况时，说明正在猜：

- 推理或输出中出现“应该”“大概”“一般来说”“通常”“我假设”“看起来”“估计”“先这样”
- 没有读对应代码，就对它的用途下结论
- 选择某个方案的理由是“常见做法”，而不是项目中的事实或用户的要求
- 准备写“如有需要可以再调整”这类话，把未确认的决定推到以后

### 先分清事实和决定

| 类型 | 例子 | 处理方式 |
|---|---|---|
| 事实问题 | 这个函数有谁调用？配置默认值是什么？测试测的是什么？ | 自己查清，不要问用户 |
| 决定问题 | 新类叫什么？预处理要不要一起换？输出维度变了能否接受？ | 必须问用户 |
| 查不清的事实 | 是否有外部仓库引用这个接口？这组超参数的来源是什么？ | 视为决定问题，问用户 |

先把能查清的事实查清，再带着调查结果去问决定问题。这样用户只需要做判断，不需要替 agent 调查。

### 可以自己决定的事情

只有以下情况可以不问：

- 项目已有明确约定，例如代码风格、目录结构、命名风格
- 本规范已经明确规定，例如不用 v2 命名、不写 fallback
- 局部实现细节，例如局部变量名、代码格式，而且不影响行为
- 用户在本轮明确说过“这部分你自己决定”

其他情况都要问。

### 两条硬性要求

1. **不能先按假设做，事后再说明。**
   - 遇到决定问题时，先停下来问，不能先做完再在报告里补一句“我假设了……”。

2. **用户授权自行决定时，必须列出所有判断。**
   - 每个自行做出的判断，都要写进最终报告的“我做的判断”部分。
   - 每一项都写清楚选了什么、为什么这样选、如果要改该改哪里。

## 执行流程

按顺序执行 A 到 G 七个阶段，不能跳过。每个阶段完成后，在回复中简要说明结果。

### 阶段 A：了解现状，确定替换关系

参考文件：change-index.md（位置部分、与 AGENTS.md 的关系）、artifacts.md（优先级部分）。

#### A.1 检查工作区和项目约定

先运行：

```bash
git status
git log --oneline -5
```

先读 AGENTS.md、CLAUDE.md 等项目说明文件，再找出：

- CHANGELOG 文件的位置和条目格式
- 实验记录文档的位置和条目格式
- 实验产物的存放规范、统一目录和目录结构
- 修改索引的位置：默认 `docs/agent-index/`，项目说明文件另有规定时以其为准
- 项目已有的测试、lint、类型检查命令

如果找不到 CHANGELOG、实验记录或产物目录，不要自己新建，在确认点 1 中询问用户。

#### A.2 写出替换关系（强制）

**这一步必须完成，而且必须在修改任何文件之前，完整输出给用户看。**

替换关系是后续扫描、修改、验证和最终报告的依据。没有写清替换关系，就不能进入阶段 B。

```text
## 替换关系
旧实现：ResNetEncoder（models/encoder.py）
新实现：ViTEncoder
替换原因：实验显示 ResNet 在本任务上效果较差
替换依据：用户说明 / 实验记录中的某条记录 / 结果文件路径
新方法来源：论文 / 官方代码仓库 / 用户提供的实现
新方法参数来源：官方默认配置 / 用户指定 / 待确认
修改范围：编码器本身、注册与配置、训练和评估入口、测试、文档
不在范围内：数据预处理、训练循环、日志系统
不再保留：ResNet 结构、ResNet 专属参数（depth、width_multiplier）、预训练权重加载逻辑
保持不变：对外接口仍为 encoder(images) -> features，输出维度不变
旧标识（已知部分）：
  - 代码：ResNetEncoder、build_resnet、ResNetBlock
  - 配置：encoder: resnet、resnet_depth、width_multiplier
  - 字符串：“resnet”（注册名）
  - 文档术语：ResNet、残差网络、residual
```

要求：

- 每一项都要填写。
- 填不出来的项不能猜，写成“待确认”，并在确认点 1 中提问。
- “旧标识”是开始前已知的部分。阶段 B 扫描中发现新的旧标识时，要补充进来。
- 替换关系经用户确认后，才能进入阶段 B。
- 后续发现替换关系需要调整时，必须触发确认点 3。

#### A.3 确认点 1：开始前确认

向用户确认以下事项：

1. **替换关系**：完整展示 A.2 的内容，重点确认修改范围、不在范围内的内容和“待确认”项。
2. **工作区状态**：有未提交的改动时，说明有哪些改动，询问是先提交、保持不动并继续，还是先暂停。
3. **是否先提交回退点**：方便出问题时整体回退。未经用户同意，不执行 `git commit`。
4. **修改索引的位置**：项目中还没有修改索引时，告诉用户将在 `docs/agent-index/` 创建，并确认。
5. **替换范围中的歧义**：例如“换掉 encoder”是否包括预处理流程。
6. **缺失的项目约定**：例如找不到 CHANGELOG、实验记录文档或产物目录时，询问位置或处理方式。

第 1、2、3 项必须确认；其余各项没有对应情况时可以省略。

### 阶段 B：修改前扫描整个项目

参考文件：**scanning.md（必须读）**、change-index.md。

这是最关键的一步，也是最容易被跳过的一步。搜索只能找到“已经知道要搜什么”的内容，所以替换前必须**逐个文件阅读，判断每个文件是否与旧方案有关**。搜索只作为扫描后的交叉检查，不能代替阅读。

步骤概要（具体做法见 scanning.md）：

1. **B.1 建立文件总表**：列出所有文件并分类，确定哪些要扫描。
2. **B.2 确定阅读范围**：先读 AGENTS.md、CLAUDE.md；再用修改索引把文件分成“必须阅读”和“可以跳过”。没有修改索引时全部阅读。需要阅读的文件超过 100 个时，先告诉用户再开始。
3. **B.3 逐个阅读**：读整个文件，给出“修改 / 删除 / 无关”的结论，补充旧标识清单。
4. **B.4 追踪调用关系**：向上查调用方，向下查依赖，从入口走一遍实际运行路径。
5. **B.5 交叉检查**：用旧标识搜索整个仓库，命中项必须都位于已阅读文件中。
6. **B.6 判断外部调用方**：存在可能时，在确认点 2 中询问。
7. **B.7 输出扫描覆盖报告**。

不能以“文件太多”为理由，自行跳过没有索引记录的文件。

### 阶段 C：输出清单，停下来等用户确认

参考文件：scanning.md（清单格式部分）、asking-user.md。

先用两三句话直白说明影响范围，再给出受影响文件清单，同时提交：

- 扫描覆盖报告
- 项目中已有的 fallback：位置、触发条件、触发后走的路径、默认建议
- 新名称的选项和推荐理由（有多个合理选项时）
- CHANGELOG 和实验记录的条目草稿。实验结论和数字只能来自用户说明或真实的结果文件；缺少依据的部分留空并询问，不能编造
- 本次替换会产生的实验产物会放到哪里

**输出清单后，必须停下来等待用户确认。**

- 用户回复前，不修改任何文件。
- 用户对清单的修改，例如“第 3 行不删”“第 11 行也要改”，以用户回复为准。

### 阶段 D：原地替换

参考文件：**rules.md（必须读）**。

#### D.1 修改顺序

1. 实现本身：把旧实现改成新实现
2. 导出和注册：更新 `__init__`、注册表、工厂函数
3. 调用方：所有调用位置直接使用新实现
4. 配置：配置键、配置值、默认值、配置文件
5. 测试：测试新行为
6. 当前文档：README、docs、docstring、注释，以及用户确认要更新的 AGENTS.md、CLAUDE.md
7. 历史文档：在 CHANGELOG 和实验记录中追加已确认的条目

#### D.2 修改要求

- **能修改现有文件，就不要新建文件。** 新实现写在旧实现原来的位置。
- **新增函数前，先查是否已有同类函数。** 有就复用或修改，没有才新增。
- **调用方直接使用新实现。** 不加转发函数，不加别名。
- **不写 fallback。** 出错时直接报错，并给出清楚的错误信息。认为某处确实需要 fallback 时，触发确认点 3，不能先写上。
- **只修改用户确认过的内容。** 调用方中的无关代码不要修改；第三方代码只在用户确认后修改。
- **接口有变化时，所有调用方都要同步修改。** 不能只改一部分。

#### D.3 确认点 3：遇到清单外的情况

执行中遇到以下情况，立即停下并询问用户：

- 发现清单中没有的受影响文件
- 某处修改会改变清单中没有提到的对外行为
- 测试失败，而且无法判断是实现问题还是测试仍在验证旧行为
- 发现某个计划删除的内容其实还有其他使用者
- 需要修改第三方代码，但用户之前没有确认
- 替换关系（A.2）需要调整
- 认为某处需要 fallback

询问时说明：发现了什么、对原计划有什么影响、有哪些处理方式、推荐哪一种及理由。

### 阶段 E：删除旧代码及残留

参考文件：rules.md。

#### E.1 先删除清单中已确认的内容

- 旧实现的类、函数和文件
- 旧方案专属的配置文件和配置项
- 用户确认删除的 fallback
- 只测试旧行为的测试
- 当前文档中描述旧方案的段落和示例

#### E.2 继续删除连带产生的死代码

删除旧实现后，可能出现新的未使用代码。重复以下步骤，直到没有新的死代码：

```text
1. 列出刚删除内容所依赖的辅助函数、类、常量、import
2. 逐个检查：除了刚删除的代码，还有没有地方使用？
3. 没有其他使用者：删除
4. 有其他使用者：保留
5. 对新删除的内容重复第 1 步
```

如果连带删除的内容不在已确认清单中，而且不只是未使用的 import，就触发确认点 3。

#### E.3 判断是否只服务于旧方案

同时满足以下条件，才能删除；只要有一条不确定，就询问用户：

- 当前代码中，除旧实现外没有其他引用
- 不属于通用工具，例如日志、IO、随机种子设置
- 不是公共 API 的一部分
- 不是用户明确要求保留的内容

#### E.4 agent 永远不删除的内容

以下内容只由用户删除，agent 不删除、不移动、不重命名：

- 实验结果、指标文件
- 训练日志、TensorBoard 记录
- 模型权重、checkpoint
- 数据集和数据缓存
- 用户手写的笔记
- 未被 Git 跟踪的文件

这些内容如果与旧方案有关，只在最终报告中列出，交给用户处理，见 artifacts.md。

### 阶段 F：同步文档和修改索引

参考文件：change-index.md（更新部分）。

#### F.1 当前文档

需要同步：README、`docs/`、docstring、行内注释、配置文件中的注释、notebook 中的说明和示例、命令行 `--help` 文本，以及用户确认要更新的 AGENTS.md、CLAUDE.md 段落。

修改原则：

- 只描述当前状态，不写“原来是什么、现在改成什么”。
- 示例命令必须能在当前代码下运行。
- 删除整段方法说明时，检查目录、索引和交叉引用，不要留下失效链接。
- 文档中的参数表与代码中的实际参数一一对应。

#### F.2 CHANGELOG 和实验记录

- 写入用户在确认点 2 中确认过的条目，不擅自增加内容。
- 遵循项目已有的格式、位置和语言风格。
- 实验记录中的数字、结论必须有依据，并写明对应的结果路径。
- 不修改已有的历史条目。

#### F.3 修改索引

新增本次修改记录，并更新文件职责表。内容哈希必须在所有修改完成后计算。具体做法见 change-index.md。

### 阶段 G：验证

参考文件：**verification.md（必须读）**。

以下检查全部通过，才能报告完成。命令见 verification.md。

1. **G.1 旧标识残留**：除白名单外，搜索结果为零。
2. **G.2 版本化、备份和临时文件**：没有本次新增的这类文件或目录。
3. **G.3 过渡标记**：本次新增的代码中没有 legacy、TODO remove 这类标记。
4. **G.4 fallback**：没有新增 fallback，仓库中没有退回旧实现的路径。
5. **G.5 运行检查**：运行项目已有的测试、lint、类型检查。
6. **G.6 最终改动**：每个新增文件都有必要，每个删除文件都在已确认清单中，没有修改无关文件。

检查未通过时，回到对应阶段修复，然后重新执行全部检查。

#### G.7 确认点 4：完成后确认

按 verification.md 中的格式输出最终报告，然后询问用户：

1. 是否提交 commit。如果需要提交，给出建议的 commit message。
2. 报告中列出的实验产物如何处理。agent 只提供整理建议，不执行删除、移动或重命名。

报告完成前，逐条检查：

```text
- [ ] A.2 替换关系已完整输出，并经用户确认

- [ ] 交叉检查的所有命中项都位于已阅读文件中
- [ ] 确认点 2：清单已经得到用户确认，修改没有超出确认范围
- [ ] 清单中每一行都已处理
- [ ] 清单外的新情况都已触发确认点 3
- [ ] 没有新增版本化名称、备份文件或归档目录
- [ ] 没有注释掉的旧代码、兼容别名、转发函数或新旧切换开关
- [ ] 没有新增 fallback；用户要求的 fallback 会输出日志，并已写进报告

- [ ] 测试针对新实现，没有通过删除测试、跳过测试或放宽断言来规避失败

- [ ] 自行做出的判断都已列出；没有自行判断时写“无”
```
